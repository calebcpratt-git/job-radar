# Job Radar — App Expert

Job Radar is Caleb's personal job-search automation: a single Python script that runs every morning in GitHub Actions, pulls postings from named-company ATS boards plus two broad job-search APIs (JSearch and Adzuna), filters them against criteria in `config.yaml`, keeps everything posted in the last 30 days, and commits a static HTML dashboard served by GitHub Pages.

**Purpose and goals.** It exists so the user (currently searching for Product Operations roles in NYC, 1–3 yrs experience) sees a fresh, filtered brief of relevant postings without visiting job boards manually. Design goals: zero paid services (free-tier Adzuna and JSearch keys; every ATS endpoint below is a keyless public API/page), zero infrastructure (GitHub Actions + Pages do everything), one user-editable file (`config.yaml`), and resilience (one broken source never kills the run). Keep these in mind when proposing changes — solutions requiring servers, databases, or paid APIs cut against the app's philosophy.

**Architecture history (important):** the app used to track named company ATS boards and flag postings that were "new since last run" via a committed `seen_jobs.json` state file. That entire model is gone — there is no state file and no new-flagging. The app shows a **rolling 30-day window** of everything currently matching. Named-company tracking was later re-wired in a CSV-driven form: `ats_fetch.py` reads `ats_map.csv` (company, ats platform, endpoint URL, optional `waas_slug`) and dispatches each row to the matching fetcher, covering seven ATS platforms (see "Per-source API details" below). `main()` calls `get_all_ats_jobs()` **before** the broad sources so ATS-board results win dedupe over aggregator duplicates. Toggle this on/off via `ats_map.enabled` in `config.yaml`; the earlier token-based `fetch_greenhouse`/`fetch_lever`/`fetch_ashby`/`fetch_companies`/`ATS_FETCHERS` functions (driven by a `companies:` config list) were removed as dead code once this superseded them — if you see a reference to that shape, it's stale.

## Data flow (main() in job_check.py)

1. **Load config** → `criteria` dict: `location`, `location_aliases`, `remote_ok`, `max_days_old`, `digital_signals`, `title_rules`.
2. **Fetch named-company ATS boards** (`get_all_ats_jobs()` from `ats_fetch.py`) if `ats_map.enabled` (default true): reads `ats_map.csv`, dispatches each row to the fetcher matching its `ats` column, normalizes into the common job schema, then tags every job `group = "target"`. Runs **before** the broad sources so ATS-board postings win dedupe over aggregator duplicates of the same job. See "Per-source API details" for the 7 platforms covered and their quirks. One bad row (dead board, API change) logs to stderr and is skipped — never kills the run.
3. **Fetch Adzuna** (`fetch_adzuna`) if `adzuna.enabled`, tagged `group = "other"`: paginated (`pages` × `results_per_page`), stops early on a short page. `what_or` (the server-side keyword filter) is **not set in config** — it's built each run from `title_rule_words(criteria["title_rules"])` (see below), so Adzuna's own search always covers the same universe of words `title_rules` filters for locally; adding a rule to `title_rules` widens Adzuna's query automatically. Passes `where` (location) and `max_days_old` server-side. Reads `ADZUNA_APP_ID` / `ADZUNA_APP_KEY` from env; if missing it **skips with a stderr warning rather than failing**. Ids look like `az:<id>`. Captures both `location` (display name, often just a neighborhood) and `location_area` (full area hierarchy) for location filtering.
4. **Fetch JSearch** (`fetch_jsearch`) if `jsearch.enabled`, tagged `group = "other"`: Google for Jobs aggregator (surfaces LinkedIn, Indeed, Built In, etc.) via `api.openwebninja.com/jsearch/search-v2` with `x-api-key: JSEARCH_API_KEY`. Loops over `jsearch.queries` (a plain list of natural-language phrases in config, e.g. `"product operations in new york"`) — **one API call per query**, regardless of `pages`: `num_pages` is a page *count* bundled into a single response, not a page number. Results are nested under `data.jobs`. Maps `max_days_old` to the coarse `date_posted` buckets (today/3days/week/month). Ids look like `js:<job_id>`; `source` is `JSearch (<publisher>)`. Missing key → stderr warning + skip; a single query failing (timeout/429/etc.) logs `! JSearch query '<query>' failed: ...` and just skips that query, not the whole fetch. **Do not build this as one query combining many terms with OR/parentheses** — see "Known operational realities": the field is natural-language-only, and boolean syntax degrades results rather than broadening them. `title_rule_words()` (used for Adzuna's `what_or`, see above) is a shared helper — union of every word across all `title_rules`, first-seen order — but it is deliberately *not* used to build the JSearch query for this reason.
5. **Filter** everything through `matches()` (semantics below). `group` rides along on the job dict untouched by filtering. `main()` builds two criteria dicts — the configured `criteria` for `group == "other"` jobs, and a copy with `max_days_old` forced to `None` for `group == "target"` jobs — so Target Companies postings are never age-filtered, only Other Postings are.
6. **Dedupe, two passes**: first by `id` (fallback `url`), first occurrence wins; then by normalized `(title, company)` pair to kill the same posting arriving from multiple aggregators. Fetch order = priority order (ATS boards → Adzuna → JSearch), so an ATS-board copy of a posting wins over an aggregator's copy of the same job — including its `group`, so a job found via both a target company's board and JSearch is correctly kept as "target".
7. **Sort** by `posted` descending (jobs with no date sort last).
8. **Render** into `TEMPLATE` via `.format()`, writing to `OUT_PATH` — `docs/index.html` when the `GITHUB_ACTIONS` env var is `"true"` (set automatically by Actions), otherwise `docs/preview.html` (gitignored) for local runs, so a local run can never touch the real dashboard. `render(jobs, label)` splits the final job list by `group` into `target_jobs` (`group == "target"`) and `other_jobs` (everything else) and builds each tab's `<li>` rows separately via `render_rows()`. Header shows "{n} matches" for the target-jobs total (no day-window text — Target Companies isn't age-bounded, see step 5); each tab button shows its own count.

## Filtering semantics (matches()) — the usual source of "why isn't X showing?"

- **title_rules** (config): a list of rules; each rule is a list of words. A title passes if **any one rule** matches, and a rule matches when **all of its words** appear in the title as whole words (title is tokenized with `re.findall(r"[a-z]+")`, so punctuation/hyphens split words but "ProductOps" stays one token and fails). A **single-word rule** (e.g. `[implementation]`, `[bizops]`) is valid and matches on that one word alone — the code just does `all(w in words for w in rule_words)`, which is trivially true for a one-element list — so those rules are much broader than the two-word AND rules. Rules as of 2026-07-16 span seven groups (see `config.yaml` for the exact list, which is the source of truth): the original product/ops variants (`[product, operations]`, `[product, ops]`, `[platform, operations]`, `[business, operations]`, `[strategy, operations]`, `[revenue, operations]`, `[product, analyst]`); product strategy & analytics (`product`+`strategy`/`analytics`/`specialist`); deployment / forward-deployed (`deployment`+`strategist`/`manager`/`associate`/`specialist`/`lead`, plus `[forward, deployed]` and `[deployed, intelligence]`); implementation (`[implementation]`, single-word); customer success & post-sale (`customer`+`success`/`operations`, `onboarding`+`manager`/`specialist`, `engagement`+`manager`/`associate`); solutions non-engineering variants (`solutions`+`consultant`/`associate`/`specialist` — deliberately excludes Solutions Engineer/Architect); and generalist ops (`gtm`+`operations`/`ops`, `sales`+`operations`, `growth`+`operations`, `[bizops]` single-word, `[chief, staff]`). If `title_rules` is empty, falls back to hardcoded product + (operations|ops). There is **no salary filter** anymore — salary is display-only.
- **digital_signals** (config): if the job has a non-empty description, it must contain at least one signal substring (software, saas, platform, api, roadmap, agile, ux, etc.) — filters physical-product/CPG/logistics ops out. **Jobs with no description are kept.**
- **location** (`location_ok()`): a job's location text (`location + " " + location_area`, lowercased) is checked against `location_aliases` (config) — a whole-word/phrase match via regex (`\b(?:alias1|alias2|...)\b`), **not** a plain substring check, so a short alias like `"queens"` doesn't false-match inside an unrelated word like "Queensland". `location_aliases` defaults to `[location]` if unset in config; as configured it's `["new york", "new york city", "nyc", "manhattan", "brooklyn", "queens", "bronx", "staten island"]`, so any of those — not just the literal string "New York" — counts as an NYC match. This closes the old "Brooklyn, NY" / "Manhattan" borough gap (both now match directly via their own alias) without needing a spelled-out "New York" anywhere in the text.
  Behavior beyond the alias match splits by `group` (see "Data flow" step 2–4):
  - **Other Postings** (`group != "target"`, Adzuna/JSearch): unchanged — a job passes if it matches an alias, **or** `remote_ok: true` and `looks_remote(job_loc)` (any remote job, regardless of where else it's tied to).
  - **Target Companies** (`group == "target"`, ATS-board jobs): a job matching an alias **always** passes, even if also remote-flagged (e.g. "New York, NY (Remote)" — the NY office is an option, so it's kept, unlike Other Postings' logic this isn't gated by `remote_ok`). A job that does *not* match an alias but *is* remote-flagged passes only if it names no other specific place: `_words(job_loc) - _REMOTE_FILLER_WORDS` (filler = `{remote, us, usa, u, s, a, united, states, the, in, only}`) must be empty — so `"Remote"`, `"Remote (United States)"`, `"Remote - US"` pass (could plausibly be worked from the NY office), while `"Remote - India"`, `"Madrid (Remote)"`, `"UK - Remote (Remote)"` are excluded (tied to a different specific place). A job with neither an alias match nor a remote flag is excluded outright.
- **max_days_old** (30): checked inside `matches()`, but as of 2026-07-27 only for `group == "other"` (Adzuna/JSearch) jobs — `main()` passes a criteria copy with `max_days_old` forced to `None` for `group == "target"` jobs, so ATS-board postings are never age-filtered locally (Adzuna/JSearch still map `max_days_old` server-side too, see "Data flow" steps 3–4, but that's irrelevant to `target` since ATS boards don't go through those fetchers). Parsed with `datetime.fromisoformat` after `Z`→`+00:00`; **unparseable or missing dates are kept**.

Adzuna also applies its own server-side keyword layer (`what_or`, derived from `title_rule_words(title_rules)` — see "Data flow" step 3, not a config value anymore) before the local filters — an Adzuna posting must survive both.

## Known operational realities

- **The dashboard is ~100% JSearch-dependent.** Adzuna typically contributes 0–2 jobs/day; JSearch supplies essentially everything. Each JSearch query is capped at whatever `pages` is (~10 results/page by Google relevance) means real matches can simply never enter the pipeline — when a "direct match" is missing, check source coverage *first*, filters second.
- **Sources fail soft.** A dead API key, rate limit, or API change produces a stderr warning, an empty result set, and a **successfully committed 0-match dashboard with a green Actions run**. Diagnose via the "Run job check" step log: look for `! JSearch query ... failed:` / `! Adzuna page N failed:` vs `· JSearch broad search: 0 postings`. (A patch adding a `raw == []` guard that exits 1 and injects a stale-data banner into the existing dashboard, plus `if: always()` on the commit step, may have been applied — check `main()` for `mark_dashboard_stale`.)
- **JSearch's `query` field is natural-language-only, not boolean** (confirmed 2026-07-16 against OpenWeb Ninja's own docs and live A/B tests): `"(product operations OR chief of staff) in New York"` returns *fewer*, less relevant results than either phrase alone — the API doesn't parse OR/parentheses as logic, it just gets confused. Broadening JSearch coverage means adding more short, separate, plain-language entries to `jsearch.queries` (currently 4: `"product operations in new york"`, `"operations manager in new york"`, `"forward deployed implementation manager in new york"`, `"customer success solutions consultant in new york"`) — never combining terms into one query. Bumping `pages` does not compensate for a narrow/malformed query; results per query saturate independently of page count once the underlying search has nothing more to return (tested 10 vs 20 vs 30 vs 50, no gain beyond a query's own saturation point).
- **JSearch is noticeably flaky under load.** Testing on 2026-07-16 (repeated runs of the same 4 queries within a short span) produced inconsistent per-query failures — some client-side read timeouts (20s `HTTP_TIMEOUT`), some upstream `504 Endpoint request timed out`, and eventually explicit `429` rate-limit responses after enough back-to-back calls. Higher `pages` per query makes individual calls slower and more likely to time out (at `pages: 30`, 3 of 4 queries failed vs 1 of 4 at `pages: 10`). Treat a partial/empty JSearch result as possibly transient, not necessarily a broken key or query — retrying later (not immediately, to avoid compounding rate-limiting) often succeeds.
- **JSearch free tier** is ~200 calls/month; call cost scales with number of queries (1 call/day/query), so with 4 queries configured that's ~120–150 calls/month at once/day — keep the `queries:` list short and be mindful that manual/local test runs consume the same quota as the scheduled workflow.
- **ATS boards contribute little under the current title_rules** — though this note predates the 2026-07-16 title_rules expansion. `ats_map.csv` is mostly AI/fintech/proptech startups; their listings skew Engineering/Sales/GTM, not classic Product Operations, so historically only a handful of ~3,000 fetched ATS postings survived `title_rules`. The expanded rules now include customer success, onboarding, solutions, implementation, and forward-deployed titles — role types these startups commonly post — so ATS-board contribution may rise; hasn't been re-measured against a live run yet.

## Deployment & operations

- **Secrets** (GitHub repo Actions secrets → env vars): `ADZUNA_APP_ID`, `ADZUNA_APP_KEY`, `JSEARCH_API_KEY`. Never hardcode. Local runs can use a `.env` file (loaded by `_load_dotenv`, never overrides real env vars).
- **Workflow**: checkout → Python 3.12 → `pip install -r requirements.txt` → `python job_check.py` → commit `docs/index.html` as `job-radar-bot` (`|| echo "No changes"` prevents failures on empty commits). Requires `permissions: contents: write`.
- **Pages**: deploy-from-branch, `main` / `/docs`. Dashboard URL: `https://calebcpratt-git.github.io/job-radar/`.
- **Vercel (mirror deployment + resume-tailoring function)**: the same repo is also linked to a second Vercel project named `get-rich-radar` (team: `team-caleb1`), which serves the identical `docs/index.html` dashboard **and** hosts `api/generate.py` as a Python serverless function at `/api/generate` (see "Resume tailoring" below). Vercel assigns this one project several domain aliases for the same deployment — `get-rich-radar.vercel.app` (short, canonical — the one `RESUME_API_BASE` in `job_check.py` points at), `get-rich-radar-team-caleb1.vercel.app`, and `get-rich-radar-git-main-team-caleb1.vercel.app` (tracks the `main` branch). All three (plus the GitHub Pages host) are in `api/generate.py`'s `ALLOWED_REFERER_HOSTS` — if the dashboard is ever viewed from a URL not in that list, "Tailor resume" 403s with a "Blocked" page, so check the actual Vercel project domains (not just what's documented here) before assuming that list is complete. A `vercel.json` at the repo root is required and must look like this:
```json
  {
    "$schema": "https://openapi.vercel.sh/vercel.json",
    "framework": null,
    "outputDirectory": "docs",
    "buildCommand": null,
    "installCommand": null,
    "functions": {
      "api/generate.py": { "maxDuration": 60 }
    }
  }
```
  Without `framework: null` + `outputDirectory: "docs"`, Vercel auto-detects "Python" (because `requirements.txt` and `job_check.py` sit at the repo root) and fails with `No python entrypoint found` — there is no root-level entrypoint because this isn't a Python web app, it's a batch script that writes static HTML. Note `buildCommand`/`installCommand` must be JSON `null`, not `false` — Vercel's schema rejects `false` there. The static-site settings (`outputDirectory`, `buildCommand: null`) do **not** block `api/generate.py` from being built — Vercel builds files under `api/` through a separate, non-configurable pipeline (its own `pip install -r requirements.txt`) regardless of the top-level build/install command, so the static mirror and the Python function coexist in one deployment with no conflict. `functions.maxDuration` is required because the default Vercel function timeout is far shorter than a Claude Opus call can take.
  Vercel auto-redeploys on every push to `main`, including the daily bot commit from `job-check.yml`, so the Vercel mirror (and the function) refresh on the same cadence as GitHub Pages with no extra config.
  **Redeploy gotcha**: Vercel's dashboard "Redeploy" button rebuilds whatever commit the *original* deployment was on — it does not pull latest `main`. If troubleshooting a failed deploy, always check the commit SHA in the build log's `Cloning ... (Branch: main, Commit: ...)` line against the current `main` HEAD before assuming a fix didn't work. To force a build of the true latest commit, push a fresh commit (`git commit --allow-empty` works) rather than clicking Redeploy on an old deployment.
  **Required env var**: `ANTHROPIC_API_KEY` must be set on the Vercel project (Project Settings → Environment Variables) — it is not a GitHub Actions secret, since `api/generate.py` never runs in Actions. Without it, `/api/generate` returns a 500 with a clear "not set" message rather than crashing opaquely.
- **Local run (dashboard)**: set the three fetch-source env vars (or `.env`), `python job_check.py`, open `docs/preview.html` (not `docs/index.html`) — `OUT_PATH` in `job_check.py` checks `os.environ.get("GITHUB_ACTIONS") == "true"` and only points at `docs/index.html` when that's set, which happens automatically in Actions and never locally. This means `docs/index.html` can no longer be regenerated or overwritten by a local run at all — it's gitignored via `docs/preview.html` in `.gitignore`. No state file otherwise, so local runs are harmless.
- **Local run (resume function)**: `api/generate.py` is written against Vercel's Python runtime (`BaseHTTPRequestHandler`-based `handler` class, working directory = repo root) and isn't meant to run standalone locally — test it by deploying to Vercel (a preview deployment is fine) and hitting the URL directly, or with `vercel dev` if that's ever set up.

## Dashboard behavior

Self-contained generated HTML (Google Fonts only external dependency): header with "{n} matches" (`<span id="match-count">`; count reflects only what's actually listed on the page — no day-window text, since Target Companies, the one visible tab, isn't age-bounded — and updates live as filters are applied, see "Client-side filters" below), then a two-column `.layout` — a `.sidebar` (the Companies filter) and `.main` (tab bar, controls, job list, footer) — inside the `.wrap` container (widened from 760px to 980px to fit the sidebar; below 760px viewport width the layout stacks to a single column). **One visible tab** — "Target Companies" (postings with `group == "target"`, i.e. from `ats_map.csv` boards) — with a count badge in the tab button and a `<ul class="job-list">` of `<li class="job">` rows (title link, company, location, salary if known, source · posted-date meta line, plus a "Tailor resume ↗" link — see "Resume tailoring" below) and its own empty state ("No target-company matches today…"). The "Other Postings" tab (Adzuna + JSearch broad search, `group == "other"`) has been pulled from `TEMPLATE` for now — no button, no `<ul>` — but this is display-only: `main()` still fetches Adzuna/JSearch and tags their jobs `"other"`, and `render()` still computes `other_jobs`/`other_body`/`other_count` (now unused `str.format` kwargs), so those postings are fetched and filtered same as before, just not shown anywhere. Salary formatting via `fmt_salary`, relative dates via `fmt_posted` (both driven by the shared `days_old()` helper — whole days since `posted`, or `None` if missing/unparseable). Colors/typography are CSS variables at the top of `TEMPLATE`. Because `TEMPLATE` is filled with `str.format`, **literal braces in any CSS/JS added there must be doubled (`{{ }}`)** — forgetting this raises `KeyError`/`IndexError` at render time. Job fields are escaped with `html.escape`. There is no "new" pill or new-only toggle anymore.

A job's tab placement is decided once, at fetch time, by the `group` field set in `main()` (`"target"` for ATS-board jobs, `"other"` for Adzuna/JSearch) — see "Data flow" step 2–4 — and `render()` splits on it before building rows for each group, though only the `target` rows currently reach `TEMPLATE`. To bring the Other Postings tab back, re-add its button/`<ul>` to `TEMPLATE` and reference `{{other_rows}}`/`{{other_count}}` — `render()` already produces them, nothing in `main()` needs to change. To add a third tab or re-source a tab, change what sets `group` in `main()`, not `render()`.

**Client-side filters (all in the inline `<script>`, purely front-end — no fetch/config involvement):** every `<li class="job">` carries `data-company` (company name, trimmed + lowercased, the matching key) and `data-posted-date` (UTC calendar date `YYYY-MM-DD` from `posted_date_str()`, or `""` if `posted` was missing/unparseable — treated as "always shown," mirroring `matches()`'s own handling of unparseable dates). Three controls share one `filterState` object (`{{search, companies, sinceDate}}`) and a single `computeVisible(el)` predicate that ANDs all three together; `applyFilters()` re-evaluates every job's `style.display` whenever any control changes, and also recounts however many stayed visible and writes it into the header's `#match-count` span (`"{n} matches"`) — so that header count always reflects the current filtered set, not the total. This replaced the old standalone search-only `apply()` function — the search box (`#q`) behavior is unchanged (still filters `.job` items by substring), it just now writes into `filterState.search` instead of setting `display` directly.
- **Posted since** (`#date-filter`, a native `<input type="date">` in `.controls` next to the search box, with a "Posted since" label and `max` pinned to today's UTC date so a future date can't be picked): picking a date sets `filterState.sinceDate` to that `YYYY-MM-DD` string; a job is hidden when its `data-posted-date` is a non-empty string earlier than `sinceDate` (plain ISO-date string comparison — no `Date` parsing). `data-posted-date=""` always passes. Clearing the input (browsers show a native "×" once a date is set) sets `filterState.sinceDate` back to `null`, showing everything again. `posted_date_str()` (near `days_old()`/`fmt_posted()` in `job_check.py`) is the Python-side source of `data-posted-date`, converting a job's `posted` ISO timestamp to its UTC calendar date.
- **Companies** (`.company-filter` in `.sidebar`): a checkbox per distinct company, scoped to whichever tab is currently active — `buildCompanyFilter(tabKey)` rebuilds the checkbox list from only that tab panel's `.job` elements' `data-company` (deduped by that key, labeled with the original-case company name read from `.company`'s text, not derived from the lowercased key, sorted alphabetically). This tab-scoping is vestigial while only the `target` tab exists (the `panels` map in the inline `<script>` now has just a `target` entry) but is left in place since it costs nothing and is what re-enabling Other Postings would rely on. Called once on load for the default tab (`'target'`) and again on every tab-button click, right after the `hidden` toggle — it also resets `filterState.companies` to a fresh empty `Set` each time. The list box is capped at `max-height:310px` with `overflow-y:auto` on `.company-filter-list` — sized for ~10 rows at the current row padding/font-size before it scrolls. Zero boxes checked = no company filtering (shows all); checking one or more shows the union of matching companies (`filterState.companies` is a `Set`, checked via `.size > 0`).
- Adding a fourth filter: follow the same pattern — add a field to `filterState`, a branch in `computeVisible()`, and a control that updates state then calls `applyFilters()`. Don't reintroduce direct `style.display` writes outside `applyFilters()` or a new filter will silently fight with the existing ones.

## Resume tailoring

Each job row's "Tailor resume ↗" link (`.tailor-btn`, built in `render_rows()`) is a plain `<a>` to `RESUME_API_BASE + "?" + urlencode({title, company, location, url})` — `RESUME_API_BASE` is hardcoded in `job_check.py` to the Vercel domain (`https://get-rich-radar.vercel.app/api/generate`), since only Vercel can run the function; GitHub Pages can't, so the link works the same whichever mirror the dashboard is being viewed from. This is a static link, not JS — clicking it fires exactly one GET request for exactly that job, opened in a new tab (`target="_blank"`). Nothing runs for other postings and nothing runs on page load; there is no bulk-generate anything.

**What `api/generate.py` does, in order:** (1) checks the `Referer` header against `ALLOWED_REFERER_HOSTS` (both dashboard hostnames) and 403s anything else — see "Not real authentication" below; (2) best-effort fetches the job's own posting page server-side and strips it to plain text for extra context, capped at 6000 chars — failure here is soft, generation still proceeds on title/company/location alone (consistent with the fail-soft convention elsewhere in this repo); **if the stripped body text is under `MIN_BODY_TEXT_LEN` (200 chars)** — the signature of a client-side-rendered posting page (Ashby, and likely other JS-SPA boards) whose raw HTML body is just a "you need JavaScript" shell — it falls back to the `<meta name="description">` / `og:description` tag content instead, since ATS SPAs commonly embed the full JD there for link-preview/SEO purposes even though the rendered body is empty without JS; (3) loads `resume/master_resume.yaml` (the factual bullets) and `resume/experience_bank.yaml` (extra accomplishments); (4) calls the Claude API (`ANTHROPIC_MODEL` env var, default `claude-opus-5`; `ANTHROPIC_EFFORT`, default `medium`) with `output_config.format` set to a strict JSON schema (`RESUME_SCHEMA`), asking it to rewrite each role's bullets for the specific posting — reordering/rephrasing only, never inventing new facts — and to pick one optional section (a personal project, a leadership program, or neither); (5) renders the result into a self-contained, print-ready HTML page (own inline CSS, `@page` sized to a US letter page, a "Print / Save as PDF" button) and returns it directly as the response. There's no PDF library involved — the user prints/saves as PDF from the browser.

**Claude API call timeout/retries.** The `Anthropic` client in `_generate_bullets()` is configured with `timeout=110.0, max_retries=1` (as of 2026-08-13). This was raised from the original `timeout=55.0` with the SDK's default `max_retries=2` after a prod 502: the current prompt asks for a `{role}_reasoning` scratchpad plus bullets for all 6 roles, which can genuinely take close to a minute to generate, and the old settings meant one slow-but-real call got retried twice — three full 55s attempts back to back (~166s total) before the SDK gave up and the endpoint 502'd. Retrying doesn't help when a call is slow rather than flaky, so per-attempt headroom was raised and retries cut to fail fast after one retry instead of three. If this endpoint starts 502'ing again after further system-prompt changes (more roles, longer reasoning, etc.), suspect the same failure mode first — check Vercel runtime logs (`get_runtime_logs`/`get_runtime_errors` on project `get-rich-radar`, team `team-caleb1`) for a `! Claude API error: Request timed out or interrupted` line before assuming something else broke. Note there's no `functions.maxDuration` override in `vercel.json`, so the platform-side execution limit is whatever the account's default is — if that default is shorter than the client timeout, the platform will kill the function first regardless of what the client is configured to wait for.

`RESUME_SCHEMA` requires a `{role}_reasoning` string per role alongside `{role}_bullets` — a short scratchpad note on which 2-3 source facts for that role are most relevant to the posting and why. Reasoning fields are generated but never rendered (`_render_resume_html()` only reads `{role}_bullets`); they exist to improve fact selection during generation and to make prompt evaluation possible by exposing the model's reasoning.

**One-page fit is enforced primarily through per-bullet character limits, not bullet count alone.** Each role in `master_resume.yaml` still carries a `bullet_target` count, but `SYSTEM_PROMPT` also enforces a hard 122-character ceiling and a 110-character soft floor per bullet, with an explicit push toward the top of that range (116-122) rather than letting bullets cluster near the floor — an earlier version of this prompt (100-118) technically fit the page but produced bullets that visibly under-filled the line, because models default toward the low end of a wide range unless told not to. **`font-size` is 9.3pt and `@page` margin is `0.4in 0.5in`** (as of 2026-08-06) — these two numbers are load-bearing for the character limits above; if either changes, re-measure and update the limits in `SYSTEM_PROMPT`'s `<constraints>` block in the same commit.

**Why 9.3pt and not the visually-matching 10pt of the base resume:** `resume/Caleb_Pratt_Resume.pdf` was exported with real embedded Calibri (confirmed via `pdffonts`), where a 127-character bullet renders at ~530pt wide — fits comfortably in the ~540pt-wide printable column (0.5in margins, US letter). The `font-family` stack (`Calibri, Carlito, Candara, Segoe, "Segoe UI", Optima, Arial, sans-serif`) is an attempt to reproduce that, but **none of Calibri/Carlito/Candara/Segoe are installed on a stock Mac** — confirmed via `system_profiler SPFontsDataType` — so the browser silently falls through to `Optima` (bundled with macOS, sits before `Arial` in the stack) or, on other machines, `Arial`. Both were measured (via AppKit `NSString.size(withAttributes:)`, i.e. real installed-font metrics) at ~6–7% wider per character than genuine Calibri at the same point size — a 127-char bullet needs ~565pt in either, which overflows the ~528pt column net of list-item indent and wraps to a second line. There's no way to force real Calibri or Carlito to render without bundling a font file (out of scope for now — a real fix would embed the open-source, metrically-compatible Carlito as a `@font-face` static asset), so the workaround compensates in the other direction: **9.3pt** brings even the worst-case fallback font's width back under the available column, with the longest guaranteed-static bullet (the 127-char leadership one — always rendered verbatim, never AI-shortened) verified fitting on one line via an actual headless-Chrome print-to-PDF (`google-chrome --headless --print-to-pdf`, same rendering path as the "Print / Save as PDF" button), not just character math. The **122-character ceiling** for AI-generated bullets was derived the same way — verified against synthetic bullets at exactly 118-122 chars, rendered and printed via headless Chrome, confirmed both fitting on one line and visually filling the column close to the header rows' full width. The **110-character floor** (with bias toward 116-122) exists to counter a separate failure mode: bullets generated under an earlier, wider 85-100 and then 100-118 range clustered near the *low* end (as low as 93-108 chars) even though the ceiling had headroom, leaving the page looking sparse regardless of how generous the ceiling was — the floor has to be close to the ceiling to force full-width bullets, a wide floor-to-ceiling gap doesn't get used. If a genuine `@font-face`-embedded Carlito is ever added, both the font-size and these character limits should be revisited — real Calibri's higher legibility-per-pt likely means both can move back toward the original 10pt / larger-character figures.

**Vertical rhythm** (`.entry { margin-bottom: 11pt }`, `h2 { margin: 6px 0 3px }`) was tuned the same evidence-based way: the base resume's own `pdftotext -bbox-layout` output shows a consistent ~13pt gap between every top-level block (each company, each named section) that the generated page previously had almost none of (`.entry` was `margin-bottom: 2px`), which read as a wall of text and also meant a shrunk font-size left visibly more blank space at the bottom of the page than the base file has. The contact line was also wrong: `h['email']` and `h['phone']` were joined onto one line with a middot separator, while the base resume has them as two separate centered lines — `_render_resume_html()` now emits two `<p class="contact">` elements instead of one.

**Verification method for any future layout change to this file:** character-width math alone is not sufficient — it already produced a font-size (9.1pt, an earlier iteration) that looked fine on paper but wasn't checked against a real print, and separately missed that spacing/contact-line bugs existed at all. The reliable check is: render `_render_resume_html()`'s output to a local HTML file, then `google-chrome --headless --disable-gpu --no-pdf-header-footer --print-to-pdf=out.pdf file:///path/to/file.html` (uses the exact fonts installed on the machine, exactly like the in-browser "Print / Save as PDF" button does), then either read the PDF directly or check `pdftotext -bbox-layout` for exact positions/page count. Chrome is present on this Mac at `/Applications/Google Chrome.app`.

**Known limitation:** the model approximates character counts rather than counting exactly, so occasional bullets still exceed the stated 122-character ceiling or fall short of the 110-character floor; character count is also an imperfect predictor of wrapping, since actual rendered width depends on which letters are used. Prompt-only control is therefore approximate — a code-level width check after generation is the reliable fix if this becomes a real problem (not yet implemented). This is also why the floor/ceiling verification above used synthetic bullets built to an exact length in code, not real model output — there was no API key available in the environment where this was tuned to actually call Claude and see real generations, so the character-range choice is verified for layout correctness but not yet confirmed against genuine model behavior at scale.

**Not real authentication.** The `Referer` check is abuse-deterrence against casual crawlers and other sites embedding a link to the endpoint, not a security boundary — it's trivially spoofable outside a browser, and the repo (and therefore `api/generate.py`'s source and exact query params) is public. The actual protection is a spend limit set on the `ANTHROPIC_API_KEY` in the Anthropic Console — do that before treating this as safe to leave running long-term. There is no per-user or per-IP rate limiting; Vercel functions are stateless between invocations, so an in-memory counter wouldn't work without adding a database, which is out of scope (see CLAUDE.md).

**Extending the experience bank:** when the user mentions something they did that isn't in `master_resume.yaml`, add it as a short factual entry to `resume/experience_bank.yaml` (under the right company, or `general` if it doesn't map to one) — the generator picks it up automatically next run, no code change needed. Keep entries factual and specific, the same style as the bullets already in `master_resume.yaml`, since that specificity is what keeps the generator's rephrasing honest.

## Common tasks — how to do them right

- **Change search criteria**: edit `config.yaml` only. A filter can only keep what the sources return, so broadening usually means touching both a local layer (`title_rules` / `digital_signals`) and what the sources actually fetch — but the two source queries behave differently now: Adzuna's `what_or` is auto-derived from `title_rules` (nothing to edit there directly), while JSearch's `query` field is natural-language-only and ignores `title_rules` entirely, so widening JSearch coverage means adding another short, plain-language entry to `jsearch.queries` in config — never combining terms into one query with OR/parentheses (see "Known operational realities").
- **Add a title pattern**: append a rule to `title_rules` (all words in a rule are ANDed; rules are ORed). Whole-word matching — add singular/abbreviated variants as separate rules if needed.
- **Track a specific company**: add a row to `ats_map.csv` (`company, ats, endpoint, open_jobs, waas_slug`). `ats` must be one of `ashby` / `workable` / `greenhouse` / `lever` / `rippling` / `gem`, with `endpoint` the full API/board URL (see patterns below); or leave `ats` as `NOT FOUND` and `endpoint` empty with `waas_slug` filled in for a Work at a Startup (YC) company. Verify a new endpoint by requesting it directly before trusting it — platforms occasionally change response shape without notice. A company on an unsupported ATS or a self-hosted careers page needs a new fetcher in `ats_fetch.py` (raw fetch + normalizer returning the common job-dict shape with a unique id prefix) wired into `FETCHERS`/`NORMALIZERS` and `get_all_ats_jobs()`'s dispatch, with failures caught same as the rest.
- **Change schedule**: edit the cron in `.github/workflows/job-check.yml` (UTC!), not the root duplicate.
- **Record a new accomplishment for tailored resumes**: append it to `resume/experience_bank.yaml` (see "Resume tailoring"). Only touch `resume/master_resume.yaml` for corrections to the base resume itself — it's meant to mirror what's actually on Caleb's real resume.
- **Widen/narrow the window**: `max_days_old` in config — only applies to Other Postings (`group == "other"`, Adzuna/JSearch) in `matches()`, and maps to JSearch's coarse `date_posted` buckets. Target Companies is not age-filtered at all (see "Filtering semantics").
- **Restyle the dashboard**: edit `TEMPLATE` in `job_check.py` (double the braces), rerun, optionally sync the root `index.html` preview.
- **Debug a missing posting, in order**: (1) is it in the raw source results at all? — JSearch coverage is the top cause of misses; (2) title_rules whole-word match; (3) `location_ok()` — does the location text match a `location_aliases` entry, or (for a `group == "target"` posting) is it remote-flagged but tied to a different specific place per `_REMOTE_FILLER_WORDS` (see "Filtering semantics"); (4) digital_signals if it has a description; (5) for Other Postings only, the 30-day window (Target Companies isn't age-filtered) / unparseable date.

## Per-source API details (ats_fetch.py — 7 platforms via ats_map.csv)

All requests use a full browser-style User-Agent + `Accept` header (`DEFAULT_HEADERS` in `ats_fetch.py`) — workatastartup.com specifically 406s on a bare `Mozilla/5.0` with no `Accept` header, so don't simplify this. Ids are namespaced `<prefix>:<company-slug>:<platform-id>` (`_slug_from_endpoint` backs up one path segment when the URL ends in a literal `/jobs`, e.g. Greenhouse/Rippling).

- **Ashby** (`ats: ashby`) — `endpoint` = `api.ashbyhq.com/posting-api/job-board/{slug}`, fetched with `includeCompensation=true`. Jobs at `data.jobs[]`. Appends "(Remote)" to location when `isRemote`; extracts salary from nested `compensationTiers`; description from `descriptionPlain`.
- **Workable** (`ats: workable`) — `endpoint` = `apply.workable.com/api/v1/widget/accounts/{slug}`. Jobs at `data.jobs[]`. Location built from `city`/`state`/`country` + "(Remote)" if `telecommuting`. `published_on` is date-only (`YYYY-MM-DD`) — normalized to a UTC datetime so `max_days_old` filtering actually works; a raw date-only string fails `datetime.fromisoformat` arithmetic silently (caught and treated as "unparseable, keep"). **No description field** in this endpoint — such jobs bypass `digital_signals`. No salary data.
- **Greenhouse** (`ats: greenhouse`) — `endpoint` = `boards-api.greenhouse.io/v1/boards/{slug}/jobs`, fetched with `content=true` for the HTML description (stripped to plain text). `posted` is really `updated_at` — an edited old posting looks recent and can re-enter the 30-day window. No salary data.
- **Lever** (`ats: lever`) — `endpoint` = `api.lever.co/v0/postings/{slug}?mode=json` (query string included in the CSV row). Bare list, not `{"jobs": [...]}`. `posted` from `createdAt` epoch-ms; location from `categories.location`; salary from `salaryRange.min`/`max`; description from `descriptionPlain`.
- **Rippling** (`ats: rippling`) — `endpoint` = `api.rippling.com/platform/api/ats/v1/board/{slug}/jobs`. **Bare list**, not `{"jobs": [...]}` — a naive `.get("jobs", ...)` on the response crashes with `AttributeError` since lists have no `.get()`; `fetch_rippling` checks `isinstance(data, list)` first. Location from `workLocation.label`. No date, no salary, no description exposed.
- **Gem** (`ats: gem`) — `endpoint` = `jobs.gem.com/{slug}`, but that URL is a client-rendered GraphQL SPA with **no embedded JSON and no REST endpoint**; there is nothing to GET directly. `fetch_gem` instead POSTs a `JobBoardList` GraphQL query (reverse-engineered from Gem's own JS bundle) to `jobs.gem.com/api/public/graphql` with `{"variables": {"boardId": slug}}`. Jobs at `data.oatsExternalJobPostings.jobPostings[]`. Job URL is constructed as `jobs.gem.com/{slug}/{extId}`. **No posted-date or salary in this query** (only Gem's single-job-page query has those, which would mean one extra request per job — not fetched). Breaks if Gem changes this internal query; there is no public docs page to check against.
- **Work at a Startup / WaaS** (`ats: NOT FOUND`, `waas_slug` filled in) — **not** the Algolia search embedded on workatastartup.com: that key's baked-in `tagFilters` restriction returns zero hits for every query, including an empty one (confirmed by direct testing, despite Algolia "looking" like the obvious integration point). Instead `fetch_waas(slug)` fetches `workatastartup.com/companies/{slug}` and parses the server-rendered Inertia.js `data-page` JSON attribute for `props.company.jobs[]` — the company's own page already lists its open jobs, keyed 1:1 to `waas_slug`, no API key needed. Salary is a display string (`"$20K - $40K"`), parsed into `salary_min`/`salary_max` via regex. Job URL is `workatastartup.com/jobs/{id}`. **No posted-date or description exposed.** Breaks if workatastartup.com changes its Inertia component/props shape (no versioned public API).
- Rows with `ats: NOT FOUND` and no `waas_slug` (no usable source at all) are skipped with a stderr warning, not treated as an error.
